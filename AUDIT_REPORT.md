## Process deviations and notes

- **An earlier audit's report was in the tree.** Commit `20a788c` carried an `AUDIT_REPORT.md` of a completed audit of
  another branch (`feature/prt-audit`), while `BUGS.md` was the empty template and `bugs/` did not exist. `AUDIT.md`
  makes `AUDIT_REPORT.md` the campaign state, so the orchestrator opened it to resume, and read about the first half of
  it (summary, process, and the candidate tables of its early rounds) before recognizing it as the report of an earlier
  audit, which the blind-hunt rule forbids reading. It stopped reading there and replaced the file with this one. The
  old text remains in git at `20a788c`. Consequences and mitigations:
  - No agent of this campaign is given anything from that report. Every agent is told not to read the history of
    `AUDIT_REPORT.md` or `BUGS.md` before this campaign's first commit.
  - The orchestrator derives every angle from `THREAT_MODEL.md` and the strategies `AUDIT.md` prescribes, not from what
    it read. It only orchestrates, so it proposes no candidates itself.
  - The requester should treat the orchestrator, not the hunters, as non-blind.
- **Round order and overlap.** The requester asked for at least 10 rounds in two days. To keep that pace, round 2
  (data flow) hunts while round 1 is still in triage and proof, so its hunters got round 1's candidates with the outcome
  "pending". The variant search for confirmed bugs, which `AUDIT.md` lists second, runs as round 3, once round 1 has
  confirmations. Hunts run as several workflows side by side to reach 10 concurrent hunters. No hunter was blocked in round 1.
- **Disk filled once.** During round 1 proofs, anvil instances started by agents dumped block states under
  `~/.foundry/anvil/tmp` (one grew 12 GB in 6 minutes) and filled the disk. The orchestrator removed the dumps, killed the
  runaway anvil (the prover of R1-A7-2 was using it) and added `bugs/harness/anvil-wrap.sh`, which bounds the dumps. Agents
  running at that moment may have seen write failures.
- **Fable hunters earlier than planned.** During round 4 the requester asked that the next rounds use a few Fable
  5.2 hunters. From round 5, three of ten hunters run on `claude-fable-5-2` before any round has been clean. These mixed
  rounds do not count toward the stop rule, which needs rounds whose hunters all run on Fable.
- **Hunt ends after round 10.** During round 9 the requester asked to wind the hunt down after round 10, with no
  further rounds. The stop rule of `AUDIT.md` (three consecutive clean rounds whose hunters all run on Fable) will
  therefore not be met; the audit ends on the requester's instruction. Round 10 withholds the campaign's findings
  from its hunters, so the report can give the rediscovery count that `AUDIT.md` asks for. After round 10: finish the
  open candidates, run the second opinion on the reading-based drops and refutations of rounds 4 to 10, re-run every
  confirmed test, and write the final report.
- **Concurrency.** The workflow runtime caps concurrent agents at the CPU count minus two, which is 2 on this 4-CPU
  container, below the 10 hunters `AUDIT.md` allows.

## Gaps and ambiguities in the threat model

Raised by round 1 triage (each names the candidate that exposed it):

- Component table vs section 3: AUDIT.md assigns 'Referee verifier' to machine-solidity-step as a whole, while section 3 defines a referee verifier as one 'whose acceptance settles disputes' and support as 'copies of the verifiers whose acceptance settles nothing'. MetaStep.step in that library is never called by pinned Dave (R1-R11-1: Critical vs Medium).
- Clock sizing in the referee model: unclear whether a deployed referee's clocks sized below the worst-case R12 cost count as a defect that 'only changes how long a claim may take to respond' (support, Medium) or as an A7 failure caused by the emulator's worst-case cost (Critical). Also, section 2 bounds a correctly designed application's mcycles only, not its uarch cycles per mcycle or its input count (R1-A7-1, R1-R12-1, R1-A7-2).
- A5's 'No party can make it stop accepting them': unclear whether a privileged role the deployment configures (the rollups guardian, foreclosure) is such a party or a trusted part of the deployment (R1-A5-1).
- Section 4 says 'the manual must state this requirement', which is a requirement on the manual. No section 8 case says whether violating it is Medium ('violates a rule or the manual') or Low (R1-R14-2).
- O1/section 4: unclear whether a snapshot whose hashed contents meet every valid-template condition must stay adoptable when its cached hash-tree structure is malformed or missing, and whether a loud load error counts as 'crash the honest operator'. Non-hashed config.json fields such as hash_tree.phtc_size are neither 'cached hash-tree data' nor a valid-template condition (R1-O1-1, R1-O1-2).
- R4 configuration clause: unclear whether it binds independently of the valid-template conditions, and whether 'register values' covers uarch RAM contents given in a configuration (R1-R4-1).
- R13 'reproducibly buildable': unclear whether this requires pinned build inputs (toolchain versions, base-image digest) or only that today's rebuild matches. The High case's qualifier 'while what is deployed matches its audited source' is also ambiguous when the audited source cannot be built without a hand edit (R1-R1-1, R1-R13-1).
- Output/yield exclusion: unclear whether it excuses a per-yield cost that is bounded but larger than needed, and whether it covers console characters, which are neither outputs nor yields (R1-R8-3, R1-R14-1).
- Referee-model input record: unclear whether the input files given to the doc/recipes referee stand for the on-chain input record that any sender fills (rated as if a deployed referee had the defect) or are trusted configuration (R1-A2-1).
- R1 'Undefined behavior': unclear whether a data race or out-of-range write whose value no hash ever reads violates R1 by itself (R1-R9-2).
- Section 5 calls any disagreement between Dave and the manual's model a defect. Section 8 gives no class to a disagreement that changes no outcome, such as Dave letting anyone join inner tournaments (R1-A2-2).
- Section 3 says referee-model stalls are 'rated as support', and the support rule gives Medium when the stood-in role (a deployed referee breaking A8) would be Critical. That makes 'rated as support' almost always Medium, which may not be intended (R1-A8-3).
- Guest software 'documented use' is undefined for implicit dependencies: undocumented /tmp/merkle.dat state, and --utf8-payload with untrusted payloads although the manual's own calculator uses that mode (R1-GUEST-1, R1-GUEST-2).
- Deliberate API state change 'performed as documented': unclear when the API accepts a write to a register the manual calls 'a creation-time mode' (iunrep) (R1-R2-1).
- SHA-256 machines: R9 requires precomputed hashes to be correct for 'every supported hash function', but the manual reserves SHA-256 for the ZK prover and AUDIT.md excludes ZK proving (R1-R9-1).
- Blind-hunt rule vs R13: proving that released versions collide on machine-identification registers requires reading release tags, which are neither audit/prt2 history nor clearly 'other branches' (R1-R13-3).
- Host support: the Medium case for loud persistence failures in an 'uncommon host setup that the manual documents' depends on which hosts the manual documents, and doc/README.md names no supported OS or page size (R1-R1-2).

- Self-contradictory manual: section 8's clause 'It takes the severity it would have if the manual were right' does not say which statement governs when two manual sections contradict each other and the code matches one of them (R2-DFINPUT-1: /dev/cmio section vs HTIF section on REASON/DATA).

- R13 'reproducibly buildable from audited source': unclear whether incremental builds and Docker images built from a working tree with untracked generated files count, or only clean checkouts; build-time guards that fail open have no class (R3-VARGEN-1, R3-VARGEN-2; extends the R1-R1-1/R1-R13-1 gap).
- Fee-market inclusion: the goal assumes 'the chain includes its transactions within the dispute clocks', but section 7 lets the adversary raise unrelated chain activity; unclear whether an operator's failure to re-price within its own configured budget is excused by that assumption (R3-VARSCHED-2).
- Inclusion slack: the model does not say whether clocks must let the honest claim win in windows shorter than its inclusion time plus one block, which decides Medium vs Low for one-block mis-timing by the operator (R3-VARSCHED-1; same question as R1-A8-4).
- Restart time: R4 requires restarting after a stop and submitting within the clocks, but A7 does not say whether clocks are sized for restart time, so bounded post-stop delays have no clear class (R3-VARO2PLAYER-1, R3-VARO2PLAYER-2).
- Unhashed template fields and cost: section 8's snapshot clause ('nothing it carries outside the hashed state may affect any transition (R1), crash the honest operator, or corrupt its memory') omits cost, so distributor-set fields such as mark_pages_dirty that survive an O1 rebuild and slow later reloads have no class (R3-VARCACHE-2; extends the R1-O1-2 gap).
- Persistence after in-memory API changes: unclear whether O2's guarantee for a shared directory (destroy then sync) must also hold when an API call (replace_memory_range) changed the machine in ways the directory's config.json does not record, and whether such a call on a shared machine is 'used as documented' (R3-VARCACHE-1).
- Documentation of deviations: unclear whether threat-model statements (R8 'can never change the cycle counter') or DTB compatible strings ('riscv,clint0') count as the manual documenting a deviation, and whether guest-readable state-layout tables (PMA array) are a 'security-relevant point'; the recurring Medium vs literal-R7 Critical conflict applies again (R3-VARSPEC-1, R3-VARSPEC-2, R3-VARSPEC-3; same pattern as R2-DFGUESTSTATE-1).
- Creation-time modes changed later: R14 allows 'deliberate changes through the machine API' but rules out 'any other host input'; unclear whether a runtime-config console input source switched on after creation, or a write to a register the manual calls an initial value (htif_iconsole), is a deliberate change or host input (R3-VARSHADOW-1; extends R1-R2-1).
- CLI output as claim material: unclear whether lines printed in the claim-series format by implied options (--final-hash, start:) count as claims of 'a tool that computes claims' (R3-VARSPEC-4; extends R1-R6-1).

Raised by round 4 triage:

- Claim-computing CLI vs development tool: section 3 lists 'a tool that computes claims' as an honest-operator stand-in, while section 8 lets 'Development tools ... instead stop and report the violation' of the rollup interface. The cartesi-machine CLI's --mcycle-computation-hash/--uarch-cycle-computation-hash options fit both; which one decides Medium vs Low (R4-RGPLAYERGUEST-1; same question as R1-R8-2 for vg.lua and R1-R6-1 for the CLI printer).
- What the honest operator owes after its claim wins: R4 says it 'keeps defending its claim' and 'defends every epoch whose dispute is open', but the model does not say whether an operator process that crash-loops after the root tournament is decided (because the settled state is not stageable) violates anything, or whether this is wholly the application-stall exclusion (R4-RGEPOCHS-2, R4-RGPLAYERGUEST-2).
- Dispute constants in demonstration referees: R13 makes the dispute constants part of the protocol and the manual's hash view fixes 2^24 inputs per epoch, but the model does not say whether a self-consistent support referee/player pair (vg.lua) with a different constant is a defect, nor (already noted for R3-VARREFMODEL-3) whether vg.lua's referee is a referee model or a support component (R4-RGEPOCHS-1).
- Library defects that no current caller reaches: section 3 rates a library by 'the most critical role among the components that reach the defect through it' but does not say how to rate a defect in a documented library operation that no shipped component reaches today (presumably 'Any other support defect is Low') (R4-RGPROOF-1).

Raised by round 5 triage:

- Build configuration and assertions: R10 forbids build-type dependence only for verifiers. The model does not say whether it is a defect that the packaged honest-operator build keeps asserts live (process abort) everywhere but interpret.cpp while release=yes compiles them out, or whether formal UB (ODR-violating inline bodies, a throwing resize_and_overwrite operation) that no hash or result depends on violates R1/section 4 (R5-INVINTERP-1, R5-INVAPI-1; extends the R1-R9-2 gap).
- Failed sync followed by a successful one: O2 defines a guaranteed directory as 'synced after the last change', but does not say whether a directory whose sync failed must be discarded, or whether a later successful sync restores the guarantee when the kernel dropped the failed pages (R5-INVSTORE-1; extends the R3-VARDIRTY-2 gap on continuing after failed calls).
- O2 and template-producing tools: unclear whether a shipped tool that writes a template without syncing it (cartesi-machine --store) violates section 5's 'tools ... must follow them' when another documented route makes the directory guaranteed, and whether the honest operator's own unsynced template is covered by the O2 reload exclusion after a power loss (R5-INVSTORE-3).
- Manual crash-recovery rules: whether a recovery procedure in the manual or CLI help that designates a directory O2 does not guarantee is a manual/behavior contradiction on a security-relevant point, a support defect, or excluded by the O2 reload exclusion (R5-INVSTORE-2).
- Operator funds: section 4 lists the provisioned host resources (CPU, memory, storage) but not the operator's on-chain balance for bonds and gas; unclear whether a balance shortfall is an unprovisioned resource that 'may stop the honest operator' or a condition the operator must survive, especially when its own pending bond recovery would cure it (R5-INVBRIDGE-1).
- Transient host faults that do not stop the operator: section 4 says a host fault 'may stop the honest operator', and R4 requires restarting after a stop, but the model is silent on an operator that keeps running and permanently gives up one claim after a transient fault (R5-INVPLAYER-1).
- Per-range rebuild versus O1: unclear whether the documented mark_pages_dirty recomputation of replace_memory_range counts as a rebuild under O1 ('A defect that defeats the rebuild itself') or whether supplied tree files are trusted caller data (R5-INVHASH-1; related to R1-R11-3).
- Tip reorgs that only invalidate a read pin: section 4 excludes 'recovering when that history is replaced', but does not say whether a reorg of non-final blocks that changes no history the operator acted on, and only crashes it, is covered (R5-INVBRIDGE-2).
- Opt-out checks in claim-computing tools: unclear whether a support tool that computes claims but aborts by default on an application's interface violation, with a documented option to continue, meets R4's 'whether or not its application is correctly designed' (R5-INVBRIDGE-3; extends the R4-RGPLAYERGUEST-1 gap).

Raised by round 6 triage:

- Within-policy reorgs of the operator's own transactions: section 4 says the honest operator acts only on final history and excludes 'Acting on history before it is final, and recovering when that history is replaced', but transaction submission necessarily acts at the tip; unclear whether a shallow reorg that drops the operator's own mined transaction (and a retirement decision taken on the 'latest' nonce) is covered (R6-DYNBRIDGE-1; related to R5-INVBRIDGE-2).
- Lowered observation head over unchanged history: a reorg to a shorter branch that replaces no block the operator acted on, but crashes it, is neither a reorg deeper than the policy nor a replacement of acted-on history; with A7 silent on restart time, a crash followed by a successful restart has no clear class (R6-DYNBRIDGE-2; extends the R5-INVBRIDGE-2 and R3-VARO2PLAYER-1 gaps).
- Transient host/network faults that become a permanent, silent hang: section 4 lets a host fault 'stop the honest operator' and R4 requires a restart after a stop, but the model does not say whether operator software that hangs undetectably (defeating the restart) is covered by the host-fault exclusion (R6-DYNBRIDGE-3; same gap as R5-INVPLAYER-1).
- Persistence calls that cannot be completed after an in-process host fault: the Medium persistence case covers only 'an uncommon host setup that the manual documents, or while cleaning up after a stop'; a call whose documented retry cannot succeed after a transient fault (no wrong hash, no damaged guaranteed directory) falls to the host-fault exclusion or Low without a stated reading (R6-DYNPERSIST-1).
- R3 'trailing data' versus ignored or contradictory header fields and non-canonical encodings: the Medium/Low trailing-data case names only trailing data; whether ignored brackets/notes, log_type flags contradicting the log, or whitespace-tolerant base64 (log malleability: two byte-different logs verify) count as 'trailing data that does not affect its result' or as other log-validity conditions that R3 says 'must be rejected' is not stated (R6-DYNLOGFUZZ-1).
- Guest-tool documented use when the help text admits combinations the protocol encodes identically: yield.c's help lists modes and reasons independently; section 3's 'depends on them as documented' does not say whether every combination a tool's own help accepts is documented use (R6-DYNGUEST-1).
- Latent memory-safety defects in support libraries reachable only through trusted-caller parameters: section 4's memory-safety requirement covers paths carrying data from other parties, and the library stand-in rule rates by components that reach the defect, so a heap over-read reachable by any future caller rates Low today (R6-DYNAPI-1).

Raised by round 7 triage:

- Trailing data in tournament proofs: section 8's Medium case 'A referee verifier that accepts trailing data that does not affect its result (R3)' names verifiers and R3 speaks of transition logs; it is unclear whether ignored computation-hash proof data in the tournament's seal move (Dave _requireAgreeState at leaf 0) counts (R7-MANTOURN-1; same split as R1-R3-3).
- Dispute constants versus the normative model: section 5 makes the manual's model normative except listed simplifications and clock values, but does not say whether its demonstration dispute constants (sampling period 2^10) are normative or deployment-chosen; Dave's released period is 2^18 (R7-MANTOURN-2).
- Incomplete manual specifications of a transition: unclear whether a manual description that lists a transition's writes but omits some (the delivery's imcyclemax write and rx-buffer zero padding) is a 'contradiction between the manual and the behavior' or silence (R1-R14-2 held silence is not covered), and whether the threat model's own section 2 definition of imcyclemax supplies the missing specification (R7-MANARCH-1).
- Non-PRT verification recipes: unclear whether the manual's 'blockchain way' recipes for template instantiation and NVRAM result extraction stand in for an in-scope referee verifier (section 3 support stand-in rule; readings.md asks to check that the stood-in role exists), and whether a helper whose API leaves the root and index binding to its caller is itself a verifier defect (R7-MANHASHSTATE-1).
- Verifiers run on proofs received from others outside the honest operator's path: unclear whether a reference output-proof verifier stands in for a referee verifier, for the honest operator's 'may decline' path, or for nothing when its documented walk-through only uses the reader's own artifacts (R7-MANHASHCOMP-1).
- Host faults that delete rather than corrupt: section 4 and the host-fault exclusion forbid turning a host fault into 'a directory that O2 guarantees but that later loads as a different state', which does not literally cover error handling that deletes an O2-guaranteed directory, while section 5 forbids damaging one (R7-MANCLIROLL-1).
- The uarch memory map: R3 defines a uarch trap by 'an access that its memory map does not allow', but the manual's only description of that map ('access all memory ranges and devices visible to the main processor') does not say whether loads from device MMIO addresses or unmapped holes are allowed (native returns 0), so whether accepting them is a High trap-acceptance defect is undecided (R7-MANARCH-3, related to R1-R10-1).
- Non-hash metadata of a stored directory: unclear whether section 8's Medium case 'leaves ... a stored directory inconsistent with the machine's contents (R9)' covers fields that are never read for a transition or hash (config.json register values), and why an on-path operation with the same inconsistency but no named rule violated would rate lower than the off-path Medium case (R7-MANLUA1-2).
- Uarch-internal deviations: unclear whether the Medium case 'An undocumented deterministic deviation ... in behavior that no correct guest relies on (R7)' applies to behavior of the uarch that no guest can observe (R7-MANARCH-3).

Raised by round 8 triage:

- Chain finality vs dispute responses (R8-GOALTIMEOUT-1): section 4 says the honest operator 'acts only on history that its policy treats as final, such as finalized blocks', under a heading about the 'input policy'. The model does not say whether this binds observing match moves and responding, nor whether a confirmation-depth policy counts as 'final'. Dave's released G (5 min) assumes responses read 'latest'.
- Number of forced matches (R8-GOALTIMEOUT-2): A7 and section 7 assume 'the logarithmic number of matches that a tournament forces', and R12 sizes per-match costs by it. The manual's listed, non-normative simplification (Dave pairs each joiner with the waiting claim) lets Sybils force a linear number. The model does not say how A7 sizing applies when the deployed referee forces more matches than the normative bracket.
- Output acceptance vs execution and size (R8-GOALOUTPUT-1, R8-GOALNOPROOF-1): A5's converse ('accepts every output ... whenever its valid proof is presented') does not say whether acceptance includes executing a voucher under the chain's per-transaction limits, or only validating it (validateOutput works at any size). Section 8's Critical entry on proofs or transactions that cannot fit has an A3 exemption for inputs but no counterpart bound for outputs, and does not say whether output-execution transactions sent by parties other than the honest operator count.
- Template as settled state (R8-GOALEPOCH-2, R8-GOALOUTPUT-2): A5 says 'A valid template is such a state', but also 'The settled state is the last leaf of the winning claim'. It is unclear whether the template counts as the settled state before epoch 0 is accepted, and whether a delay in accepting its outputs breaks 'whenever'. This extends the existing genesis/non-genesis template gap (R2-DFOUTPUT-1).
- Withdrawal path (R8-GOALNODE-1): the AUDIT table names the rollups contracts' 'input box, output validation' only. Neither the AUDIT table nor the threat model covers the foreclosure/withdrawal path (accounts-drive proofs). R9's 'lost lengths' covers only 'every tree the emulator defines', not data-to-node length binding of application encodings checked by a referee contract.
- Operator behavior after a divergent settlement (R8-GOALEPOCH-1): no rule says whether the honest operator must keep defending later epochs from a settled state that differs from its own (A1 makes the on-chain settled state the next before-state), or may stop. No rule says whether it must signal during the staging period.

Raised by round 10 triage:

- Guest software and decoded field meaning (R10-PERAPPDEV-3): section 3's guest-software Critical clause speaks of deviating 'from the rollup interface' and R7 of rx-buffer 'contents'; it does not say whether a guest tool that delivers a decoded input field in a unit its own linked API document contradicts (while the manual agrees with the tool) counts as a deviation, nor which document governs a guest tool's 'documented' use when the manual and the tool's package docs disagree.
- Per-yield baseline (R10-PERGUEST-2, extends the R1-R8-3/R1-R14-1/R2-DFYIELD-1 gap): the High constant-factor case compares with 'the same operation without the defect', but when one confirmed defect's control (R1-R8-3: the ~17 always-dirty pages per yield) is itself avoidable work, the model does not say whether that baseline is 'a cost that the specified semantics require'.
- Unhashed config bytes and R12 (R10-PERTEMPLATE-4): R12 bounds loading by 'the bytes it covers'; it is unclear whether unhashed, ignored config.json bytes count as bytes the load covers (then linear cost is conformant) or as data outside the hashed state that 'may not crash the honest operator' regardless of size, and whether parse-time memory amplification of such data is a constant-factor or an unbounded-allocation case.
- Developer-time guest-tool defects (R10-PERAPPDEV-5 part c): a guest tool that, used as its API document says, makes template creation end at a non-accepted yield has no class other than Low; the model does not say whether guest-software scope covers defects that only invalidate the template rather than being triggered by an input.
