# Readings of THREAT_MODEL.md settled by the second opinion after round 3

Apply these when rating. They are readings of the text, not additions to it.

- Section 8's sentence 'Once a snapshot meets them, nothing it carries outside the hashed state may affect any transition (R1), crash the honest operator, or corrupt its memory' sits inside an out-of-scope entry and is not the full list of guarantees. If a valid template is refused loudly on the honest operator's path ('Obtaining its valid template', storing/reloading), rate it at step 4 against R4/O1. Section 8's own Medium case 'A persistence operation that fails loudly ... in an uncommon host setup that the manual documents' shows that a loud persistence failure is a defect, and only an uncommon documented host setup lowers it to Medium.
- An undocumented workaround, such as hand-editing config.json, does not make O1 'possible to follow' when the documented rebuild (the manual's `--clear-hash-tree`) is defeated. Section 5's 'A defect that defeats the rebuild itself ... is not excused by them' refers to the documented rebuild.
- When a Support component (the PRT player, the CLI) fails on its own operator path, rate it under section 3's stand-in rule ('Medium when it would rate High or Critical in the role the component stands in for'), even if the emulator component involved rates Low in its own role. Then take the most critical role among the components that show the defect. Do not stop at 'the emulator API behaves as documented'.
- A party's trust comes only from THREAT_MODEL section 4 and the listed exclusions. A code comment such as "trusted orchestration", or a manual simplification that section 5 makes non-normative, never makes a party trusted.
- For the referee model, section 3's "what it accepts or derives is rated as if a deployed referee had it" covers every message the model accepts, including control channels that have no counterpart in Dave. When there is no counterpart, rate what a deployed referee with the same acceptance would cause. Do not drop to Low because no counterpart exists.
- The exclusion 'Nondeterminism in unreproducible machines (R14)' covers only nondeterminism. A deterministic deviation in a feature that only unreproducible machines reach (VirtIO, PLIC sources) is not out of scope. Rate it with the listed cases. The Medium 'undocumented deterministic deviation' case has no reachability condition, so the absence of a reachable valid-template state does not make it Low.
- R4's configuration clause binds machine creation. Its exemptions (unreproducible, another hash function, register values the spec and manual disallow) are the full list. Do not read 'this rule' as met vacuously for configurations that are not valid templates: that makes the exemptions redundant. Do not let the general 'deliberate state change ... performed as documented' exclusion excuse accepting a configuration the clause says must be rejected.
- Section 3's guest-software Critical clause ("A defect that lets an input make such an application deviate from the rollup interface") does not require the deviation to depend on the input's content. A deviation that the delivery of any input triggers, in an application that uses the tool as documented, still counts as one an input causes. Decide guest-software findings on documented or intended use (the manual's statement of what the tool is for, and its documented formats and limits), not on whether the trigger depends on content.
- For guest software, a library or tool that neither the manual nor its own package documents (for example rollup-http-client) cannot meet "depends on them as documented". Its defects are Low unless an application relies on documented behaviour that the defect breaks.
- Rate the build recipes and Docker images in doc/ (doc/Makefile, doc/Dockerfile.prt) as Support, not as the referee model, because the AUDIT table's referee-model rows name only the doc/recipes referee model and Dave with the regenerated step. When a deploy-time or player check refuses a version mismatch they introduce, it is a loud failure, not an A6 violation by the referee model.
- When rating a Support component against the role it stands in for, apply step 4 in that role: violating a rule's wording at a reachable state (for example R11 'which no proof can select') is Critical there even without a wrong after-hash, unless a listed High or Medium case caps it. Do not refute a stand-in Critical only because no wrong acceptance was shown. First check that the stood-in role exists in scope: a copy of a main-processor step verifier stands in for nothing, because the intro excludes main-processor step proof forms.
- R9's 'Precomputed hashes ... must be correct for every supported hash function' covers precomputed values the emulator uses or reports as hashes under that function. A constant whose API documents a single hash function (for example 'the Keccak-256 hash of the pristine uarch state') and that is used only behind a check for that function does not violate R9 under other functions.

# Added by the second opinion after round 10

- Section 8's application-stall exclusion ('The stall of an application that halts ... and what the application loses by it') does not by itself end the rating of a guest-software defect at step 1. When an input makes in-scope guest software halt or stall an application that depends on it as documented, section 3's guest-software clause rates it Critical. The stall exclusion covers what an application loses by its own design, so the rating must rest on whether an input triggers it.
- For guest software, 'as documented' and 'intended use' come from the manual first. The manual limits /usr/bin/yield to 'tests and one-off demos' and to tooling 'for testing or debugging', so defects only an application using it can reach are Low under 'a defect in guest software that only an application outside its intended use can reach'. External, unpinned documents (such as an openapi file linked from a README) do not override the manual.
- A rating that rests on a premise about the honest operator, such as 'it holds its claim', 'it is always connected' or 'it is always a poster', must check that premise over the whole honest operator's path in section 2, including 'Restarting after a stop (O2)'. A premise that holds only for an operator that never restarts does not support Low.
- For a model/deployment disagreement over who may act for a claim, ask whether the honest operator, after a restart on a new identity or connection, is one of the parties that may act in the model. If it is not, the disagreement decides a timeout (A7) and is not harmless.
- R12's 'at most linear in ... the bytes it covers' for storing, loading, cloning or syncing a machine refers to the machine (its state, as R12 measures 'from a machine at its starting position'), not to unhashed bytes of the stored directory that a distributor can inflate freely (config.json members, cache capacities); reading it otherwise makes the worst case of loading a fixed machine unbounded and empties 'bounded'.
- Section 8's 'nothing it carries outside the hashed state may ... crash the honest operator' forbids the possibility: an allocation that scales without bound with unhashed snapshot content violates it even if the prover did not drive a host to an actual crash; do not refute such a finding for 'no crash shown'.
- When a Support demo stands in for an on-chain verifier of a protocol that the model does not define, first check that the stood-in operation fits the model's protocol. Examples are template instantiation by splicing an NVRAM, result extraction from a halted machine, and the non-PRT verification game with its own constants. Section 2 says a valid template is 'changed only by running it and delivering inputs'. A3 fixes the input path, A5 fixes the output path, and section 5 makes only the PRT model normative. If the stood-in operation falls outside these, no High or Critical rating exists in that role, and the support defect is Low.
- Before rating a Support library above Low, check the reachability of each caller in code. Both a guard in the caller (for example the height assert in prt.lua new_geometry) and a call pattern (expand only after an opaque query) can stop every in-scope component from reaching the defect. Under 'A library stands in for the most critical role among the components that reach the defect through it', no reaching component means Low.
- The application-stall exclusion of section 8 removes only what the application loses. A crash of an operator component (or a support stand-in for one) that a stalled guest triggers is not excluded at step 1 ('The entries about applications exclude what an application loses, never an emulator defect that its guest triggers'). It must be rated at steps 3-4 by asking whether any R4 duty (open disputes, claims, proofs) is still owed. Triage of R4-RGEPOCHS-2 cited the exclusion first but reached the right result through step 4.
